1. Submission Debugging: Correct Predictions Can Still Score Badly

The practice started with the source's submission-debugging checklist. A model can be locally excellent and still receive a terrible leaderboard score if the submission file attaches the right predictions to the wrong rows or classes.

ID order

If submission IDs are shuffled relative to the required sample-submission order, predictions can be attached to the wrong samples and the score can collapse.

Missing / duplicate IDs

Matching the row count is not enough. The submitted ID set must match the expected test ID set with no duplicates or omissions.

Class-column order

For probability matrices, the class columns must match the required order. Swapping cat and dog columns changes the meaning of every prediction.

Probability format

When the task expects multiclass probabilities, rows should be valid probability distributions and typically sum to 1.

Hard labels vs probabilities

If the metric expects probabilities, submitting only 0/1 hard labels throws away confidence information and can badly hurt the score.

Another critical check: training and inference preprocessing must match—normalization, tokenizer, resize size, and class mapping are all part of the model pipeline.

2. Strong CV, Weak LB: Debug Before Scaling the Model

The practice then jumped into the competition workflow. If the baseline CV looks strong but the first leaderboard submission is much worse, the first response should not be “use a bigger model.”

CV looks strong
LB is unexpectedly weak
Check split / leak / preprocessing / submission
Only then change the model
Reason: a pipeline or validation problem can make model tuning completely irrelevant. More capacity does not repair a broken evaluation or submission path.

3. Business Thinking: Preserve the Evidence That Creates the Label

The source's “business thinking” section asks a more fundamental question before tuning: what information causes the label to be assigned?

In the X-ray example, suppose a diagnosis depends on a tiny lesion. If aggressive downscaling makes that lesion disappear, the model no longer has access to the evidence that generated the label.

Wrong first move

Increase model size, change the backbone, or tune learning rate while the lesion is already gone from the input.

Correct first move

Preserve the relevant visual information—for example by keeping enough resolution or using an input strategy that leaves the lesion visible.

Priority rule: make sure the model can actually see the information the label depends on before optimizing how the model learns from it.

4. Data Augmentation: One Rule Comes First

The source gives one governing test for augmentation:

After the transformation, is the original label still valid?

Valid

A cat flipped horizontally is still a cat, so the transformation can teach useful invariance.

Invalid

If the label is the digit 6, rotating it 180° can turn it into 9. The transformation has changed the answer, so it should not be used as label-preserving augmentation.

5. TTA: The Simple Cat-vs-Dog Example

TTA means Test-Time Augmentation. The model is already trained. At inference time, the same test sample is shown to the same model in several label-preserving views, and the predictions are combined.

One test cat image
Original view → 0.70 cat
Horizontal flip → 0.62 cat
Average → 0.66 cat

With two predictions, the final TTA score is:

0.70+0.622=0.66
What finally resolved the confusion: TTA is not another training method. It is inference only: multiple valid views of one test sample → predict each view → average the predictions.

The intuition is that the model may be slightly unstable to harmless changes of view. Averaging several valid views can smooth that variation. The source also warns that TTA multiplies inference cost, which matters in time-limited Code Competitions.
